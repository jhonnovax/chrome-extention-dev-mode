## Project Overview

Chrome Extension (Manifest V3) that toggles development mode for on24.com domains by managing a cookie (`htm-dev-mode`) plus user-configurable **Map Local** and **Rewrite** rules, implemented Charles-style with `chrome.debugger` (Fetch domain): the page keeps its real URL/origin, only the response body (map local, read straight from disk via `file://`) or the outgoing URL (rewrite) is changed. No proxy and no local server. In DEV/PREVIEW, per-domain **Globals** (e.g. `window.isNurturePage = true`) are injected before any page JS runs via the debugger (`Page.addScriptToEvaluateOnNewDocument`); in OFF they are kept but not injected.

**Modes are per tab and never stored:** every tab starts OFF; DEV/PREVIEW picked in the popup belongs to that tab only, reloads it and applies rewrites, Map Local, cookie and globals on the fly; the tab keeps the mode while it navigates (also to other sites) until it is closed or switched to OFF. A new tab (also one opened from a DEV tab) starts OFF, and so does every tab after a browser restart or extension reload. Modes live in memory, mirrored in `chrome.storage.session` (RAM only) so a worker restart keeps them. Nothing about modes is written to `chrome.storage.local`.

**Config lives in the cloud:** rules and globals are stored in `chrome.storage.sync` (`sync-schema.js`), so they follow the Google account signed into Chrome to every Chrome profile/machine where this extension is loaded. The extension ID is fixed by the `key` field in `manifest.json` (public key; the private key is at `~/.devmode-extension-key.pem`, outside the repo, only needed to pack a CRX), so the ID is `kiodgandllfdichppoigkhkdjbajpnpn` on every machine. Modes are per tab and not stored (see above).

**Future direction (design only, not implemented):** [docs/all-browsers-proxy-engine.md](docs/all-browsers-proxy-engine.md) describes moving the engine into a local MITM proxy in `local-server/` (recreated from scratch; the old static server was removed in 1.4) so DEV/PREVIEW, Map Local, rewrites and globals work in every browser (Chrome family, Firefox, Safari); the Chrome extension stays as Chrome's UI client and config editor and configures Chrome's proxy via `chrome.proxy`. The final package is the extension plus that mandatory local companion.

## Development

No build step required. This is a plain JavaScript extension. No local server, no setup scripts.

**To test changes:**
1. Open `chrome://extensions/`
2. Enable "Developer mode"
3. Click "Load unpacked" and select this directory
4. On the extension card → Details, turn on **Allow access to file URLs** (Map Local). It is a per-extension toggle; without it the popup/options show a red hint and requests fall back to the real site.
5. After code changes, click the refresh icon on the extension card

**Testing in an isolated Chrome (without touching your profile):** branded Chrome (137+) ignores `--load-extension`. Launch `Google Chrome` from a script with `--user-data-dir=<tmp> --remote-debugging-pipe --remote-debugging-port=9333 --enable-unsafe-extension-debugging --silent-debugger-extension-api`, keep fds 3/4 open and send `Extensions.loadUnpacked { path }` over the pipe (only accepted on the pipe, not the port). Then drive it over the port: `Runtime.evaluate` in the worker target (`/json` lists `service_worker … background.js`; an idle worker wakes on any navigation) to seed `chrome.storage`, and `chrome.developerPrivate.*` evaluated in a `chrome://extensions` page target to toggle `fileAccess`, read `runtimeErrors` and `reload` (after a reload the extension comes back disabled with `unsupportedDeveloperExtension`; `chrome.management.setEnabled(id, true)` from that page re-enables it). Two static servers on `localhost` and `127.0.0.1` give a cross-site (out-of-process) iframe.

**Sync:** Chrome must be signed in with the "Extensions" sync data type on for the config to reach other machines; otherwise `chrome.storage.sync` silently behaves like local storage. Quotas: 100 KB total, 8 KB per key, 120 writes/min (one rule or one domain's globals list is one key). Sync is Chrome-only (Edge/Brave have their own sync).

## Architecture

**sync-schema.js** - Config store shared by `background.js` (`importScripts`) and `options.js` (`<script>`), exposed as `DevModeConfig`:
- Keys in `chrome.storage.sync`: `meta { schema, updatedAt }`, `rule:<id>` (`{ kind: 'mapLocal'|'rewrite', order, enabled, modes, pattern, localPath | regex, replacement }`), `globals:<domain>` (`[{ name, value }]`)
- `readConfig()` → `{ mapLocal, rewrites, globals, seeded }`; with no `meta` key it returns `DEFAULT_SETTINGS` **without writing**, so a fresh machine never overwrites cloud data. `writeSettings({ mapLocal, rewrites })` = one `set()` + one `remove()` of dropped rule keys; `writeGlobals(domain, list)`; on a never-written store it also writes the `DEFAULT_SETTINGS` rules in the same `set()`, because writing `meta` ends the defaults fallback (before this fix, saving a global on a fresh machine left the store with zero rules and Map Local silently stopped). Quota errors propagate to the caller.

**background.js** - Service worker containing extension logic:
- Manages three states: OFF, DEV, PREVIEW **per tab** (`tabModes: Map<tabId, state>`, OFF = no entry; `getTabMode`/`setTabMode`/`modeForTab(tabId, url)`/`activeTabIds`; loaded once from and mirrored to `chrome.storage.session` key `tabModes` by `loadTabStore`/`persistTabStore`). `tabs.onRemoved` → `forgetTabMode` (mode dropped, rules re-synced); `tabs.onReplaced` moves the mode to the new tab; `syncAllTabs` drops modes of tabs that no longer exist. `freshStart()` on `onStartup`/`onInstalled` removes the 1.5 leftovers (`chrome.storage.local` `domainStates`/`activeTabOnly`) and every `htm-dev-mode` cookie; `init()` also runs `removeAllDevCookies()` at every worker start.
- Cookie `htm-dev-mode=4815162342` is **never written to Chrome's cookie jar** (the jar is shared by every tab: a new tab on the same URL would be served in DEV too). `syncRules` keeps a DNR session rule (id 2) that **appends** it to the `Cookie` header (`operation: 'append'` on `cookie`, Chrome 128+) of every request of the DEV tabs (`condition.tabIds`, no domain list: iframes and other sites included, the tab's mode rules everything it loads). No domain list on purpose: DNR headers are applied *before* the debugger pauses a request, so a domain learned from a paused document would be too late for that document (verified). It is in place before the reload that follows a mode switch. Only the server reads it (nothing in `~/Projects/orion` reads it); page JS can't see it in `document.cookie`; requests without a tab (service workers, `followRedirectInWorker`) don't carry it. Cross-site iframes get it too, so no partitioned (CHIPS) copies are needed any more. The network trace marks it as `+ htm-dev-mode (tab rule)`.
- `getConfig()`/`getSettings()` read the sync store through `DevModeConfig` with an in-memory cache invalidated on `storage.onChanged` (area `sync`). `migrateLocalConfig()` (on `onInstalled`) moves pre-1.4 `chrome.storage.local.settings/globals` into sync once, only when the sync store is still empty.
- **Interception:** tabs whose **top-level** URL is on a domain in DEV/PREVIEW get `chrome.debugger.attach` + `Fetch.enable` (`attachTab`/`detachTab`/`syncTab`/`syncAllTabs`; `tabStatesFor` returns the tab's mode, `[]` when OFF). **The tab's mode rules everything the tab loads**: CDN assets and iframes of other domains; OFF on the tab means OFF inside its iframes (no interception, no cookie, no globals). Patterns = a `Document`-only `*` pattern (always, so every top-level and iframe document is paused), the `REDIRECT_PATTERNS` (XHR and Fetch at the **Response** stage, always, see *Cross-origin redirects* below) plus the raw map-local globs of the state, or `*` + `REDIRECT_PATTERNS` when any rewrite rule applies (`interceptPatterns`). The DEV cookie rule covers every request of the tab, so `gateway.on24.com` embedded in a DEV `gatewayqa.inbfw.com` tab is served in DEV. **Iframes:** cross-site iframes are separate DevTools targets, so the root session sends `Target.setAutoAttach {flatten: true, waitForDebuggerOnStart: true}` (re-sent on every `enableInterception`); `Target.attachedToTarget` (type `iframe`) adds the child session to `childSessions`, gives it the tab's patterns (`tabPatterns`) first, then nested auto-attach, cache-off and the globals script, then `Runtime.runIfWaitingForDebugger` (always, in `finally`). Events from children carry `source.sessionId` and are answered with it (`sendCommand(tabId, method, params, sessionId)`); unknown session ids seen in events are learned back after a worker restart. On `Fetch.requestPaused` the mode is the tab's (`requestState` → `getTabMode`). Then: apply rewrites (`applyRewrites`, JS `String.replace` with `$n`) → first matching map-local rule (`mapLocalTarget`, `globToRegex`) → `fileUrlFor(localPath, lastWildcard)` (`file://` URL under the rule's folder; empty or trailing-slash paths get `index.html`; paths escaping the folder are refused) → `fetch(file://…)` from the worker (needs "Allow access to file URLs", checked with `chrome.extension.isAllowedFileSchemeAccess()` cached 5 s) → `Fetch.fulfillRequest` (200, Content-Type from the `MIME` table, base64 body) or, if the file is missing or file access is off, `Fetch.continueRequest` (with `url` when a rewrite changed it), warning once per URL. Every paused request is answered exactly once.
- Attach triggers: `setState`, `webNavigation.onBeforeNavigate` (main frame), `tabs.onUpdated` (url), `storage.onChanged` (rule keys), `init()` (re-attaches all open tabs after a worker restart). Top-level navigation-triggered attaches pass `reloadAfter: true`: when they perform a *new* attach the document request was already in flight un-intercepted, so the tab is reloaded once (in-flight attaches are deduplicated per tab in `attaching`). `onDetach` with `canceled_by_user` (user clicked Cancel on the debugging bar) marks the tab as user-detached until its next top-level navigation. A 20 s `getPlatformInfo` keep-alive runs while any tab is attached. Debugger sessions outlive the worker, so `attachedTabs` is rebuilt from `chrome.debugger.getTargets()` on startup (`ensureReady`), `detachTab` always calls `chrome.debugger.detach`, and `attachTab` re-attaches when a remembered session no longer answers. `webNavigation.onCommitted` (main frame) re-attaches a tab whose attach was refused because the previous document held another extension's frame. **OFF always wins:** `tabStatesFor(tabId, topUrl)` is the single eligibility check (`[]` when the tab is OFF or not on an http(s) page, when the tab is gone, or when it is a background tab under *Debug only the active tab*; without `topUrl` it uses `tab.pendingUrl || tab.url`, so a pending navigation to a DEV page is not mistaken for the OFF page still shown). `enableInterception` re-runs it after reading the patterns and throws `tab not eligible` instead of enabling; `attachTab` turns that into a detach (`forceDetach` inside the in-flight job, `detachTab` elsewhere), `detachTab` waits for the tab's in-flight attach before `forceDetach` so a detach requested mid-attach is not overtaken, a `Fetch.requestPaused` on an OFF tab is passed through untouched and detaches the tab, and an iframe target auto-attached on an ineligible tab is resumed and the tab detached. An OFF tab must behave as if the extension were not installed: no debugger session, no Map Local, no rewrites, no globals.
- Every attached session (root and iframe children) also gets `Network.enable` + `Network.setCacheDisabled(true)` (`disableCache`): the DNR no-cache headers only reach the HTTP cache, and the renderer's memory cache would otherwise hand back assets fetched *before* the attach (the un-intercepted first load) without any request, so the reload after a fresh attach would never see them. DEV/PREVIEW mean "cache off" anyway.
- `syncRules()` keeps `declarativeNetRequest` **session** rules (memory only): id 1, no-cache request headers with `condition.tabIds` = the DEV/PREVIEW tabs; id 2, the DEV cookie for the DEV tabs (see above); the 1.5 per-domain dynamic rules are removed once
- **Globals (injected in DEV/PREVIEW tabs only, paused in OFF):** `globals:<domain>` in sync (value = raw string). No `chrome.userScripts` (its registrations are per domain, not per tab): every attached session (tab root and auto-attached iframe targets) gets `Page.addScriptToEvaluateOnNewDocument` with `buildFrameGlobalsCode(byDomain)` (`installFrameGlobals`, `{ identifier, source }` per session in `frameGlobalsScripts`, source cached in `getFrameGlobalsSource`, rebuilt and re-pushed by `refreshFrameGlobals` inside `syncGlobals`, queued via `scheduleGlobalsSync`, run at `init()`, in `setState` before the reload, on tab close and on `storage.onChanged` for `globals:` keys). Sessions exist only on DEV/PREVIEW tabs, so the tab's mode decides. `Page.enable` is required on the session or the script never runs; the install is idempotent and adds the new script before removing the old one, because syncs run concurrently with reloads. The snippet carries every domain's list, resolves the frame's root domain at run time (`window.origin`, else nearest same-origin ancestor, else `document.referrer` / `ancestorOrigins`; covers `about:blank`, `srcdoc`, `blob:` and cross-site iframes) and injects that domain's list. Each variable is a locked accessor on `window` (getter returns the value, setter is a no-op) so it exists before any page script and survives page assignments. Values are `JSON.parse`d when possible (`true`, `42`, `{"a":1}`), otherwise kept as strings. Messages: `getState` returns the active tab's `{ state, domain, globals, usesMapLocal, fileAccess, blockedBy, interrupted }`; `setGlobals` saves the active tab domain's list to sync, re-pushes, and reloads the tab; `openExtensionDetails` opens `chrome://extensions/?id=…`.
- `storage.onChanged`: area `session` + `activeTabOnly` → tab sync; area `sync` (fires for local edits and for changes arriving from another machine) → cache invalidation, tab sync when a `rule:` key changed, globals when a `globals:` key changed.
- Generates dynamic badge icons using OffscreenCanvas, set per tab (`updateIcon(state, tabId)`)
- Auto-reloads the tab when state changes

**options.html / options.js** - Settings page (gear icon in popup, or chrome://extensions → Details → Extension options):
- Any number of Map Local (`pattern`, `localPath`, `modes`) and Rewrite (`regex`, `replacement`, `modes`) rules, each with an enabled flag
- Validates regexes with `new RegExp`, writes through `DevModeConfig.writeSettings`; a sync/quota error is shown in the footer and nothing is saved. "Restore defaults" uses `DevModeConfig.defaults()`.
- **Activity** section: the worker keeps its last 1000 `[Dev Mode]` console lines in memory (plus unhandled rejections / uncaught errors). A network trace (`traceNetwork`, fed by the `Network.*` events of every debugged session) logs each `Document` request (with its initiator: the script URL:line that navigated, e.g. to a login page), its redirects and status, the **names** of the cookies sent (blocked ones first, with Chrome's `blockedReasons`) and the `Set-Cookie` names of the response, marking cookies the server deletes (`Max-Age=0` / past `Expires`); XHR/fetch only when something was blocked, a cookie is set, or the answer is 401/403/3xx. A 401/403 line repeats what the request carried: cookie names, whether `htm-dev-mode` was among them, and request header names. `net` lines keep up to 4000 chars (others 600). URLs go through `safeUrl` (origin + path + parameter names) and cookie values are never logged, so the log can be pasted safely. Console methods are wrapped at the top of `background.js` (`activityLog`); `getActivityLog` returns them with the tab modes (`modes: [{ id, mode, url }]`), file access state and, per debugged tab, its URL, number of attached iframe sessions and Fetch patterns. The page polls every 2 s while visible, has Refresh and Copy buttons. This is the first thing to ask for when "it does not work": a request that is not listed never reached the interception.
- Banner under the title: file access state (`chrome.extension.isAllowedFileSchemeAccess()`, click → extension details); each Map Local rule shows the last file the worker served or failed to find (`getMapLocalStats` message; a folder cannot be probed from an extension page because Chrome only lists `file://` directories on navigation). Re-renders on remote sync changes when no input is focused.

**popup.html / popup.js** - Dropdown menu UI:
- Styled dark theme dropdown with three options, gear button to settings
- **Globals** section below the modes: saved variables render as inline chips `name = value` with × to delete, plus a name/value form with + (Enter also adds). Editing saves via `setGlobals` and keeps the popup open while the tab reloads. Hidden on non-http(s) tabs. When the tab is OFF the section gets `.disabled`: a "Not injected while Off" badge, grayed chips/inputs, inputs and buttons disabled
- `#file-access` line: shown only when the active mode uses a Map Local rule and "Allow access to file URLs" is off (click → extension details)
- Communicates with background.js via chrome.runtime.sendMessage

**manifest.json** - Extension configuration (Manifest V3):
- `key`: fixed public key → stable extension ID (needed for `chrome.storage.sync` to be the same store on every machine)
- Permissions: `cookies`, `debugger`, `declarativeNetRequest`, `tabs`, `webNavigation`, `scripting` (frame guard, DOM scans), `storage`
- Host permissions: `<all_urls>` (covers `file://` once the toggle is on)

## Key Implementation Details

**States:**
| State | Icon | Label | Cookie | Cache | Rules |
|-------|------|-------|--------|-------|-------|
| OFF | Gray | OFF | not sent | enabled | none (tab detached) |
| DEV | Green | DEV | sent by this tab only (`htm-dev-mode=4815162342`, DNR header rule, never in the jar) | disabled | rules whose `modes` include `dev` |
| PREVIEW | Yellow | PRE | not sent | disabled | rules whose `modes` include `preview` |

**Settings model** (`chrome.storage.sync`, one key per rule; `DEFAULT_SETTINGS` in sync-schema.js is returned while the store is empty):
```js
'rule:ml-orion':           { kind: 'mapLocal', order: 0, enabled: true, pattern: 'https://*/view/orion/*', localPath: '/Users/jnova/Projects/orion/static', modes: ['dev','preview'] }
'rule:rw-production-hash': { kind: 'rewrite',  order: 1, enabled: true, regex: '/(.*)/dist/production-(css|js)-(.*).(css|js)(.*)', replacement: '/$1/dist/production-$2.$4', modes: ['preview'] }
```
`readConfig()` hands them to the rest of the code in the old array shapes: `{ mapLocal: [{ id, enabled, pattern, localPath, modes }], rewrites: [{ id, enabled, regex, replacement, modes }] }`.

**Globals model** (`chrome.storage.sync`):
```js
'globals:.on24.com': [{ name: 'isNurturePage', value: 'true' }]   // per root domain
```

**Request flow (Fetch domain):** Rewrite runs before Map Local, so in PREVIEW `…/dist/production-js-<hash>.js` → `…/dist/production-js.js` → `file:///Users/jnova/Projects/orion/static/labs/dist/production-js.js`, while the page still sees the hashed URL. HTML documents and iframes are mapped the same way as assets (no origin change, cookies and same-origin API calls keep working), including cross-site iframes (own debugger session), which get the tab's mode, cookie and globals (e.g. the EH embed tester `https://gatewayqa.inbfw.com/view/orion/test/embed-tester.html` embedding `https://gateway.on24.com/wcc/eh/…` through `embed.js`). `localPath` is synced as typed; on a machine where the folder does not exist the options page flags it and requests fall through to the real site.

**Known QA quirk (not extension-related):** `gatewayqa.on24.com` landing pages sometimes answer a Tomcat default 404 when the page is *reloaded* shortly after loading (any reload, including Cmd+R with the extension disabled). Verified 2026-09-24: identical requests replayed with curl always get 200; the 404 arrives on a reused keep-alive connection. Mode switches reload the tab, so they can surface it. Infra issue (load-balancer persistence), reported by the user.

**Tabs Chrome refuses to debug (other extensions' frames):** Chrome closes an extension's debugger session (`onDetach` reason `target_closed`) as soon as a frame of **another extension** starts loading anywhere in the tab, and `chrome.debugger.attach` fails with *"Cannot access a chrome-extension:// URL of different extension"* while one is present. Password managers inject such frames next to inputs: **iCloud Passwords** (`pejdijmoenmkgeppbflobdenhhabjlaj`) does it on the EH embed tester (textarea) and the EH page (search box). Every request made until the re-attach escapes Map Local / Rewrite, which shows as intermittent 404s on lazy-loaded chunks. Verified 2026-09-25 in an isolated Chrome 154 with a test extension injecting a frame: the session dies with or without `Target.setAutoAttach`; removing the element from a content script (MutationObserver) is too late, the check runs when its navigation starts; a page CSP `frame-src` without `chrome-extension:` does **not** block extension frames (they bypass page CSP), so do not retry that. There is no way to keep such a tab reliably debuggable from the extension. What the code does: `reportBlockedTab` finds the culprit by scanning the page DOM for `chrome-extension://` frames (`chrome.scripting.executeScript`; `webNavigation.getAllFrames` hides them; `chrome.debugger.getTargets` type `other` as fallback) and logs it once per tab (`blockedTabs`); `onDetach(target_closed)` counts the interruption (`interruptedTabs`, reset on top-level navigation) and `retryAttach` removes foreign frames (`sweepForeignFrames`) and re-attaches after 150 ms, up to 5 times per page load (`attachRetries`). The **frame guard** (`frame-guard.js`, registered on every http(s) page while any tab is DEV/PREVIEW with `chrome.scripting.registerContentScripts` by `syncFrameGuard` inside `syncGlobals`; it asks `frameGuardStatus` at start and is pushed `frameGuard` on attach) removes foreign extension frames from debugged tabs so the re-attach can succeed. The popup shows a red line (blocked: nothing mapped; interrupted: N× during this load, some files came from the real site) that opens the extension's details. **The fix is on the user's side:** set that extension's Site access to "On click" (it stays installed and fills when its toolbar icon is clicked), or use a Chrome profile without it for development. Errors carrying that message elsewhere are silenced (`isForeignFrameError`).

**Cross-origin redirects under interception (Chrome bug, verified 2026-10-13, Chrome 155):** while *any* `Fetch.enable` pattern is active on a target (request or response stage, even a glob that matches nothing on the page; `patterns: []` is fine), Chrome mishandles a fetch/XHR that a server redirects to another origin. Locally the redirected request leaves **without its `Origin` header** (passing it back through `Fetch.continueRequest` headers does not help), so the CORS response is rejected (`Failed to fetch`). On the on24 admin it is worse: the Zendesk widget (`zendeskService.js`) fetches `wccorionqa…/webcast?command=wccorionsso&action=redirect&…`, which answers 302 to `wccqa…?…token=…` (→ `/webcast/webapi/zendesk/jwt`), and that redirect **crashes Chrome's network service** (`Network service crashed or was terminated, restarting service` in Chrome's log). Session cookies live only in the network service's memory, so every session cookie of every site is lost (`JSESSIONID`, `wcc_admin`, `qa_wcc_admin`, `BIGipServer*`, `TS*`, `htm-dev-mode`): all APIs answer 401 and the app redirects to `/webcast/login`. Only happens logged in (logged out the handoff just redirects to login). Fix: `REDIRECT_PATTERNS` pause XHR/fetch responses; `crossOriginLocation` spots a 3xx whose `Location` is another origin and `followRedirectInWorker` follows it from the worker (`fetch` with `credentials: 'include'`, request headers minus `UNFORWARDABLE_HEADER`, 301/302/303 → GET), then `Fetch.fulfillRequest`s the original request with the final status/body, the 3xx's own `Set-Cookie` headers and, for a cross-origin original request, `Access-Control-Allow-Origin`/`-Credentials` = its `Origin`. Chrome never processes the redirect. Logged as `… ← 302 to …: followed by the extension`. Diagnosing tools that found it: the network trace in Activity, and comparing the network service PID (`ps`, `utility-sub-type=network.mojom.NetworkService`) before and after a step.

**Debugging bar:** Chrome shows *"Dev Mode started debugging this browser"* while the extension holds any debugger session. It is a **global** infobar (`GlobalConfirmInfoBar` in Chromium's `debugger_api.cc`): it appears in every tab of every window, including OFF tabs, and only goes away when no tab is debugged. Cancel on it detaches every session (`canceled_by_user`). After the extension's last detach Chrome keeps the bar for a fixed auto-close delay (`kAutoCloseDelay`, 5 s in Chromium main; observed 2–3 s), so it cannot vanish instantly. Chromium skips it only for the launch flag `--silent-debugger-extension-api` (per launch, Chrome fully quit first: `open -na "Google Chrome" --args --silent-debugger-extension-api`) or for a policy-installed extension; no extension API can hide it (verified 2026-09-29). Removing it for good means leaving `chrome.debugger`, i.e. the proxy engine in `docs/all-browsers-proxy-engine.md`. **Debug only the active tab** (always on, no UI; hidden switch `activeTabOnly` in `chrome.storage.session`, default `true`, `chrome.storage.session.set({ activeTabOnly: false })` from the worker console turns it off until the browser quits; read through the cached `activeTabOnly()`, shown in the Activity summary): `tabStatesFor` treats a background tab as OFF, so the session lives only on the active tab of each window and the bar disappears while an OFF tab is in front (it still shows in every window while any window's active tab is DEV/PREVIEW). `tabs.onActivated` re-syncs every tab of the window (Chrome's `activeInfo` has no `previousTabId`, that field is Firefox-only) so the tab left detaches and the tab entered attaches; a DEV/PREVIEW tab that navigated while detached is remembered in `pendingReload` (set in `syncTab`) and reloaded when it comes to the front (`reloadAfter`). Trade-off: a background DEV/PREVIEW tab is served from the real site until it is active again. DevTools can be open at the same time (multi-client).
